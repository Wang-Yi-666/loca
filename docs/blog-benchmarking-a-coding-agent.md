# 我给自己的 coding agent 造了套评测集，然后被自己的数字打脸了

## 「挺好用」不是数据

写 coding agent 的人都会经历同一个阶段：手动试几个任务，看它改对了文件、跑通了测试，
心满意足地觉得「挺好用的」。然后你把它交给别人，别人第一个任务就翻车。

问题在于，「挺好用」是印象，不是数据。真要把这件事做扎实，只有三个问题值得回答：

1. 它能做完**多少比例**的活？
2. 它做不完的时候，**卡在哪一步**？
3. 做成一件事要**花多少代价**？

这三个问题都要求同一件事：一套固定的任务集，和一套固定的判分口径。
换一批题、换个判分方式，数字就不可比。

于是有了 `loca bench`：36 道自带任务（14 简单 / 12 中等 / 10 困难），
并发跑，跑的是真实的执行循环和真实的工具，然后给出一份报告。

这篇文章想讲的不是那个最终数字，而是**为了让它可信，我做了哪些取舍**，
以及那些取舍最后让我看到了什么。

## 第一个陷阱：用 diff 判分

最直觉的做法是：给每题准备一份「标准答案」，然后比对模型改完的文件和标准答案的差异。

这个做法是错的，而且错得很隐蔽。

同一个需求有无数种正确写法。模型把 `if x > 0:` 写成 `if 0 < x:` 是错的吗？
它把循环改成列表推导式，是错的吗？用 diff 判分，这些全算错。
于是你测出来的其实是**「模型能不能猜到我脑子里那份答案」**，
而不是「模型能不能解决这个问题」。你花力气优化 prompt，最后优化的是拟合能力。

所以我选了**行为式判分**：不看代码，只看跑起来对不对。支持三种方式：

- `pytest`：在沙箱里跑测试套件，退出码为 0 就算过；
- `run`：跑一个脚本，比 stdout 和退出码；
- `script`：调任务自带的 `verify(workspace)`，想写多细写多细。

代价是任务作者要写得出判据。但判据一旦写好，「另一种正确写法」也能通过 ——
这才是我想要的。

## 第二个陷阱：让模型看到自己的考卷

行为式判分把判据放进测试文件之后，立刻出现一个新问题：
**测试文件放在哪？**

如果它和源码一起放进工作区，模型就能读到断言。它不需要理解需求，
只需要让断言通过 —— 而这两件事在真实场景里完全不是一回事。
更糟的是，它可以**直接改测试文件**：把 `assert add(1, 2) == 3` 改成
`assert True`，然后告诉你「测试全过了」。

解法是把判分文件放进 `hidden/`：

- 开场只把 `workspace/` 复制进沙箱，`hidden/` 一个字都不给模型看；
- 判分之前，把 `hidden/` **原样复制回来，覆盖**模型留下的同名文件。

一个测试专门钉住这条性质：让 agent 手写一个必然通过的 `test_it.py`，
结果依然是 `wrong_answer`。这个「盖回去」的动作是整套评测的信任基础。

## 第三个陷阱：题目本身是坏的

这是我花时间最多、也最容易被忽略的一环。

一道题可能坏在两个方向：

- **它根本没在测东西**：初始工作区就已经能让测试通过。模型什么都不做，
  也能拿 100% 的分数。
- **它无解**：判分器连参考答案都不接受。那么这道题报出来的每一个失败
  都是噪音，不是模型的锅。

这两种情况在写题的时候极容易发生，而且**看起来一切正常** ——
你会以为自己在测模型，其实在测自己的手滑。

所以我写了 `loca bench verify`：逐题确认「起始工作区必须判不过、参考答案必须判得过」。
它不需要 provider、不花 token，几十秒跑完 36 题。

更有意思的是它**没**抓到的东西。36 道题的自检一次全过，
但在生成题目时，我靠人工核对发现了两处更隐蔽的问题：

- 一道 JSON Pointer 题，测试要求拒绝带前导零的下标，但题面（`prompt`）
  里根本没写这条要求 —— 模型不可能猜得到；
- 一道罗马数字题，测试要求拒绝小写输入，题面同样没提。

这两处都属于「判分比题面严格」，和「题目无解」是同一个病：
**它报出来的失败不是模型的能力问题。** 自检能查「参考答案过不过」，
查不出「题面有没有把要求说全」—— 后者只能靠人读。

## 第四个陷阱：把所有失败混成一个数字

最后一个设计决定是**失败怎么分类**。

模型没做出来、harness 自己崩了、题目坏了 —— 这是三件完全不同的事，
责任方也不同。混成一个「失败率」等于把 harness 的 bug 算到模型头上。

所以每次尝试结束时会落进七个 outcome 之一：

| outcome | 含义 | 责任方 |
|---|---|---|
| `passed` | 判分通过 | — |
| `wrong_answer` | 循环正常跑完，判分没过 | 模型 |
| `max_steps` | 撞到步数上限 | 模型（或上限太紧） |
| `provider_error` | 模型 API 报错 | 网络 / 服务商 |
| `timeout` | 撞到墙钟上限 | 模型太慢 |
| `crash` | harness 抛异常 | **我的 bug** |
| `grader_error` | 判分器坏了 | **出题人的 bug** |

`grader_error` 还会在报告里被单独摘出来报警，并明写「这是任务集的 bug，
不是模型的失败」。一条坏了判分器的题，永远不该出现在「模型不行」的统计里。

## 跑分：91.7%，以及三个失败

2026-09-18，DeepSeek 默认模型，36 题各跑 1 次，4 并发：

| 难度 | 题量 | 通过 | 通过率 | tokens/通过 | 步数/通过 |
|---|---:|---:|---:|---:|---:|
| simple | 14 | 13 | 92.9% | 8,071 | 4.9 |
| medium | 12 | 12 | 100% | 12,591 | 5.7 |
| hard | 10 | 8 | 80.0% | 17,901 | 7.1 |
| **合计** | **36** | **33** | **91.7%** | **11,120** | **5.3** |

整轮 399k tokens，墙钟 67 秒。成本随难度单调上升，这个曲线很符合直觉。

真正让我停下来看的是那三个失败：

| 任务 | 难度 | 失败原因 |
|---|---|---|
| `fix-recursion-base-case` | simple | 递归改对了，但负数入参没抛 `ValueError` |
| `impl-expression-evaluator` | hard | 16 条断言过了 15 条，只差 `1++2` 这种畸形输入没被拒 |
| `impl-word-wrap` | hard | 返回字符串，而契约要求返回「行的列表」 |

三个失败**没有一个是算法写不出来**。全都是同一件事：
**题面里明确写了、模型没有逐条落实的边界条件和返回类型契约。**

而且注意第一个：它是一道 **simple** 题。简单题的失败率（92.9%）反而低于
中等题（100%）—— 这不是巧合，它说明失败跟题目难度关系不大，
跟「这道题的验收条件有多具体」关系更大。

最扎眼的是 `impl-word-wrap`：它只花了 **4 步**就交卷了。
不是做不出来，是**没意识到自己没做对**。判分器是隐藏的，
它没有可运行的反馈信号，于是写完就以为完事了。

## 评测集真正的价值

如果只看 91.7% 这个数字，很容易得出「还行」的结论然后关掉页面。
但这套评测集真正给我的东西，是那三个失败的**共性**。

它们指向的问题不是「模型不够强」，而是：

- 验收标准没有被显式地摆到循环面前；
- 循环在收工之前，没有自己按题面逐条核对一遍；
- 模型缺少一个「我到底做对了没有」的反馈信号。

这三条**都是 harness 层面能解的**，跟换一个更强的模型无关。
如果我只做了手动测试，我大概会去怪模型；做了评测，我拿到的是一个可执行的方向。

这大概就是为什么要自带评测集：**它的价值不在于那个数字，而在于它把你
下一步该干什么变得无法回避。**
