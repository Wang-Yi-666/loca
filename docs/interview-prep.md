### 0.2 一句话定位（三个长度，按场合选）

**10 秒**：loca 是我从零写的 coding agent harness —— 一个不依赖任何框架的 agent 引擎，重点是跨厂商协议统一、流式容错循环，以及一套能给自己打分的评测集。

**30 秒**：它是 `loca`，一个从零实现的 coding agent harness，用来做本地开发搭子。做了四块：把 DeepSeek / OpenAI / Anthropic 三家的 tool-use 协议统一成一套；写一个能在工具失败和模型跑偏时活下来的流式执行循环；按「每个模型步」记录可复盘的执行轨迹；最后自建 36 道题的评测集，真实跑出 pass@1 91.7%。规模是 7,840 行源码配 6,978 行测试、406 项测试全绿。

**3 分钟**：见第 1.3 节。

### 0.3 三个「主动递出去的钩子」⭐

## 1. 项目自述

### 1.1 30 秒版（同 0.2）

### 1.2 1 分钟版

> 我做了一个叫 loca 的项目，是一个从零写的 coding agent harness，没用 LangChain 这类框架。
>
> 动机是我发现大部分 agent 项目就是「提示词加 SDK 调用」，真正难的东西全在框架里，看不到。所以我把最难的那层自己写了一遍。
>
> 具体做了四块。第一块是多厂商协议，DeepSeek 和 OpenAI 共用一个兼容层，Anthropic 的差异太大，我单独写了一层纯函数的协议翻译，好处是不用发网络请求就能完整测试。第二块是执行循环，重试有个硬约束：只允许在第一个流式分片到达之前重试，因为用户已经看到的内容不能重放。第三块是状态与可观测性，会话存 SQLite 可以跨进程续聊、文件改动前会快照可以按步回滚，轨迹按「每个模型步」双写数据库和 JSONL。第四块是我最想讲的：我自己造了一套 36 道题的评测集，真实跑出 pass@1 91.7%。
>
> 规模上 harness 源码七千八百多行、测试六千九百多行，四百多项测试全绿。

### 1.3 3 分钟版（结构：问题 → 取舍 → 结果 → 反思）

1. **问题（30 秒）**：agent 项目的困难不在「调用模型」，而在三件事 —— 循环怎么在失败中活下来、上下文爆了怎么办、以及怎么知道它到底行不行。这三件事恰好是框架会替你藏起来的。
2. **四个技术选择（90 秒）**：
   - 协议分层：OpenAI 兼容层 + Anthropic 纯函数翻译层（Q7）
   - 流式重试：只在首分片前重试（Q9）
   - 上下文：摘要替代丢弃，摘要消息用 user 角色承载（Q10 / Q11）
   - 评测：判分文件隐藏 + 行为式判分 + 任务集自检（Q22 / Q23 / Q28）
3. **结果（30 秒）**：给数字（0.1 那张表里挑 4 个说），重点说 **pass@1 91.7%、33/36，以及 hard 组只有 80%**。
4. **反思（30 秒，这段最加分）**：三个失败里没有一个是因为算法写不出来，全是题面写明的边界条件和返回类型契约没有逐条落实。其中一个只花了 4 步就交卷 —— 它不是做不出来，是没意识到自己没做对。这指向 harness 层的问题：**验收标准没有摆到循环面前，循环收工前也没有自己核对一遍**。

## 2. 动机与定位

### Q1 为什么做这个项目？

**先说**：为了把 agent 工程里最容易被框架藏起来的那一层，自己写一遍。

- 市面上学 agent 的路径基本是「提示词 + LLM SDK」，再往上就套框架。但循环、重试、上下文预算、错误恢复恰恰是最难也最有工程含量的部分。
- 另一个动机是：**「agent 好不好用」几乎没有可复现的数字**。我想给自己造一把尺子。
- 附带收益：跨厂商协议差异是个很实在的工程问题，DeepSeek / OpenAI / Anthropic 三家的 tool-use 消息结构、流式事件、结束原因都不一样。

**别踩**：不要说「为了做作品集」。可以说「为了做作品集，但我选了一个能真正学到东西的切法」——诚实且不扣分。

**可能追问**：为什么不用现成的 agent 框架？→ Q2。

### Q2 为什么不用 LangChain？是重新发明轮子吗？

**先说**：我并不是什么都自己写——SQLite、jsonschema、Rich、FastAPI、三家官方 SDK 我都用现成的。我只自研「会被框架藏起来的那一层」。

判断标准很清楚：**这一层是不是我要学的东西**。
- 执行循环、重试语义、上下文压缩、评测设计 → 自己写（这正是学习目标）
- 存储引擎、JSON Schema 校验、终端渲染、HTTP 框架 → 用现成的（重写没有学习收益）

**别踩**：不要贬低框架。可以说「框架在工程上是对的，只是我的目标不是最快交付，而是看清内部」。

**可能追问**：那你不是重复实现了框架已有的能力？→ 不同点在于**可观测性是我的一等公民**：框架不会告诉你「第 3 个模型步的 prompt 是多少 token、哪个工具花了多久、这次失败属于七类里的哪一类」（Q14、Q25）。

### Q3 和 Cursor / Claude Code 什么关系？有什么不同？

**先说**：定位不同。它们是产品，我做的是引擎层（harness）。

- 相同点：核心都是「模型 → 工具调用 → 结果回灌 → 再决策」的循环。
- 不同点有两个：
  1. **可观测性与可评测性是我的一等公民** —— 每一步可复盘、有可复现的分数。
  2. **厂商协议差异被当成架构问题处理**，而不是散落的 `if provider == ...`。
- **诚实的差距**：功能上比它们差得远 —— 我没有 LSP 索引、没有专门的 diff 应用引擎、没有多文件重构能力、没有 IDE 集成。我的 4 个工具是「能读、能写、能改、能执行」的最小闭环。

**别踩**：不要声称功能对标。主动说差距反而显得清醒。

### Q4 你为什么只支持 Windows？

**先说**：这是刻意的取舍，不是没做适配。

- 目标是「本地 Windows 开发机上的单用户 agent」。多平台分支只会引入**没人跑的代码路径** —— 我一开始确实有 POSIX 分支，结果是永远走不到、还挂着一个条件跳过。后来整个清掉了。
- 所以 `shell` 工具固定走 cmd.exe，系统提示词里明确告诉模型用 `dir` / `type` / `del` / `findstr`，而不是 `ls` / `cat` / `rm` / `grep`。
- 工具名也叫 `shell` 而不是 `bash` —— 原来叫 `bash` 名不副实，改了名，转录标签同步改成 `<shell ...>`。

**可以主动展开的原理**（面试官会喜欢）：CLI 的 `--workspace` 我加了校验，拒绝 `/d/repo` 这种 Git-Bash 风格的路径。因为 `ntpath` 会把它当成「盘符相对路径」，静默解析成 `D:\d\repo` —— 一个空目录，agent 于是在一个空工作区里干活而你完全不知道。这类 bug 不报错、只是结果不对，所以宁可拒绝也不猜。

**可能追问**：那用户如果用 Linux 怎么办？→ 现在会直接不支持；要支持的话，改动集中在 `shell.py` 的 `_shell_executable()` 和格式化命令的 `_format_command()` 两处，其余分层是可以复用的。

### Q5 为什么只接三家厂商 / 只做四个工具？不嫌少吗？

**先说**：三家和四个工具覆盖了「形态」而非「数量」。

- 厂商：三家已经覆盖两种协议形态（OpenAI 兼容协议 + Anthropic 独立协议）。再加一家 OpenAI 兼容的，只需三个类属性（`name` / `default_base_url` / `default_model`）；真正的工作量在**新协议**上，而再加第三种协议边际学习收益低、维护成本高。
- 工具：4 个是「能读、能写、能改、能执行」的最小闭环。加工具本身不是难点——难点在循环和评测。而且工具注册表是开放的，加一个工具的边际成本很低。

**别踩**：不要说「时间不够」。要说「我按学习收益排序，把时间花在了循环和评测上」。

## 3. 架构与设计取舍（重头戏）

### Q6 整体架构讲一下（可能让你画图）

**先说**：五层，从上到下是 CLI/Web → 执行循环 → Provider 抽象 → 工具协议 → 持久化与可观测。

```
┌─────────────────────────────────────────────────────────┐
│ 界面层   cli.py（8 个子命令，argparse + Rich）            │
│          web/（FastAPI + SSE）                           │
├─────────────────────────────────────────────────────────┤
│ 执行循环 core/loop.py  AgentLoop                         │
│   ├── core/recovery.py   退避重试（只在首分片前）         │
│   └── core/context.py     token 预算 + 摘要压缩           │
├─────────────────────────────────────────────────────────┤
│ Provider 抽象 providers/                                 │
│   ├── openai_compat.py  ← DeepSeek / OpenAI 共用         │
│   └── anthropic.py      独立纯函数翻译层                  │
├─────────────────────────────────────────────────────────┤
│ 工具协议 tools/（base + registry + validation +          │
│   filesystem + shell）                                   │
├─────────────────────────────────────────────────────────┤
│ 状态与观测 observability/                                │
│   ├── storage.py     SQLite（sessions/messages/          │
│   │                   checkpoints/traces/meta）           │
│   ├── checkpoint.py  文件快照 + 按步回滚                  │
│   ├── trace.py       事件 sink，按模型步记录              │
│   └── reporter.py    报表（Rich）/ JSON 双输出            │
└─────────────────────────────────────────────────────────┘
                    ↑ 旁挂
            eval/  评测框架（tasks / benchmark / report）
```

**讲图的关键句**：`AgentLoop` 只依赖 `LLMProvider` 和「工具列表」两个抽象；`checkpoint_manager` / `context_manager` / `recorder` 都是**可选注入**，不传就没有这个能力。所以循环本身可以脱离数据库和轨迹系统单独测试。

### Q7 三家 provider 的协议差异具体在哪？为什么这么分层？

**先说**：差异比想象的碎，分五处。

| 差异点 | OpenAI 兼容 | Anthropic |
|---|---|---|
| system 提示 | 放在 `messages` 里（role=system） | 顶层 `system` 参数 |
| 工具结果 | 独立的 `role=tool` 消息 | user 消息里的 `tool_result` block |
| 模型的工具调用 | `message.tool_calls` | content 里的 `tool_use` block |
| 流式 | `choices[0].delta` 碎片；工具参数是 **JSON 字符串碎片**，要自己拼接 | `content_block_start` / `delta` / `stop` 三类事件；工具调用在 `content_block_stop` 才完整 |
| 结束原因 | `finish_reason` | `stop_reason`（`tool_use`→`tool_calls`，`max_tokens`→`length`） |
| 附带 | — | `cache_read_input_tokens` 要计入 prompt token |

**为什么这么分层**：DeepSeek 本来就是 OpenAI 兼容协议，两者共用一个 `OpenAICompatibleProvider`（子类只覆盖 `name` / `default_base_url` / `default_model` 三个类属性）；Anthropic 差异太大，硬套会用一堆 `if` 污染主路径，所以单独做一层。

**加分句**：Anthropic 这层我做成了**纯函数翻译层** —— 请求翻译、响应翻译、流式事件翻译都是纯函数，所以 **33 项测试完全不发网络请求**。协议适配层最该长这样。

**可能追问**：三家一致性怎么保证？→ 有专门的跨厂商 parity 回归测试（19 项），钉住同一个任务在三家上产出的工具调用和流式结果一致。

### Q8 重试为什么自己写，不用 tenacity？

**先说**：因为「流式场景下什么时候允许重试」这个语义，通用重试库表达不干净。

- 通用库的心智模型是「一个函数调用，失败就重试」。但流式的关键是**已经产出过内容就不能重试** —— 一旦第一个分片已经 yield 给用户，重试会导致内容重复，更糟的是工具调用可能被**重复执行**（写文件调两次）。
- 用生成器表达最直接：`try` 只包住「还没吐字」的阶段，一旦 yield 了第一个 delta，后续错误不再重试，而是作为 `error` 事件上报。
- 所以早期确实用过 tenacity，后来移除了 —— 现在全仓库零依赖，退避逻辑在 `core/recovery.py` 里自研。

**可能追问**：退避策略是什么？→ 指数退避 + 上限，重试次数可配；provider 层还提供 `on_retry` 钩子（目前 loop 没接，见 Q43 相关的诚实回答）。

### Q9 流式下重试难在哪？「首个分片之前」怎么界定？

**先说**：难在「不可逆的副作用」。文字吐出来就收不回，工具可能已经执行了。

- 界定：`AgentLoop` 消费 provider 的流式事件。在收到第一个 `delta_text` / `delta_tool_call` **之前**发生异常 → 可以安全重试（外部看不到任何东西）。**之后**发生异常 → 不重试，转成 `error` 事件。
- 为什么重要：agent 的工具调用有副作用（写文件、跑命令）。如果重试发生在工具已经执行之后，同一条命令可能跑两次。
- 实现位置：`core/recovery.py`（退避）+ `core/loop.py`（事件消费），有 25 + 6 项测试钉住。

**别踩**：不要说「重试就是再调一次」。一定要点出「副作用不可逆」这个层面。

**可能追问**：那不可恢复的错误怎么办？→ 以 `error` 事件呈现，**不掐断 SSE 连接**。传输层始终是良构的，前端能拿到结构化的错误而不是断流。

### Q10 上下文超预算怎么处理？

**先说**：让模型把旧轮次压成摘要，而不是直接丢。

- 直接丢旧消息会丢信息，尤其是「用户要求过什么」这类约束。压缩成摘要能保住语义。
- 实现：`core/context.py` 的 `ContextManager` 管预算；接近上限时把**较旧**的消息交给模型摘要，最近若干个轮次原样保留（`--keep-recent` 可调）。
- 摘要**钉在窗口里**，不参与后续裁剪 —— 否则摘要自己被裁掉，等于白压。
- token 计数：`tiktoken` 是**可选**依赖，try-import，缺了回退到启发式估算。这样核心安装不必背上一个只在估算 token 时才用到的包。

**可能追问**：预算和是否持久化是一回事吗？→ 不是，这点我踩过坑，见 Q45。

### Q11 为什么摘要消息用 user 角色承载？

**先说**：因为存成 system 会在回灌历史时被过滤掉。

- 历史回灌时，system 消息的处理是特殊的（正常只有一条系统提示），中间插一条「摘要」形态的 system 会被当成异常清掉 —— 摘要就白做了，而且是**静默失效**。
- 所以摘要以 user 消息承载，加一个明确前缀 `[Earlier conversation summary]`，模型和代码都能一眼认出来。
- 这是那种「不看运行时行为就发现不了」的细节，单测里我专门钉了这条。

### Q12 为什么用 SQLite 而不是 JSON 文件？

**先说**：因为我要的四件事 JSON 文件都得自己实现一遍。

1. **事务**：`save_transcript` 是「DELETE + 批量插入」的整体重写，必须原子。
2. **外键级联**：删会话时要自动清掉它的消息和检查点，`ON DELETE CASCADE` 一行搞定。
3. **并发写**：评测 4 线程并发跑，多个进程同时写库。
4. **查询排序**：按最近更新列出会话、按步号取检查点。

**加分的技术细节**：
- 开了 `journal_mode = WAL`（读写不互斥）。
- 还加了 `PRAGMA busy_timeout = 5000` —— 因为并发跑评测时撞到过 `database is locked`，WAL 只降低了概率，没消除写-写冲突。
- 定义了 `SCHEMA_VERSION` 落在 meta 表里，Week 5 加 `traces` 表时从 1 升到 2。
- 检查点里存的是**工作区相对的 POSIX 路径**（不是绝对路径），这是为了可迁移性。

### Q13 为什么轨迹要双写 SQLite 和 JSONL？

**先说**：两个消费者，两种访问模式。

- **SQLite**：给 `loca report` 用 —— 要按 session 查、要聚合（token 求和、工具耗时统计）。查询友好。
- **JSONL 镜像**：给外部工具和人工排查用 —— 逐行 append，不受库锁影响；一行坏了只坏那一行（读取时跳过坏行，不会整个文件读不出来）。
- 读路径是 `gather()`：**DB 优先、JSONL 兜底**。库被删了或者损坏了，报告仍然能从磁盘上的 JSONL 重建出来。

### Q14 trace 为什么做成「事件 sink」，而不是在循环里埋点？

**先说**：为了不改动循环核心。

- `TraceRecorder` 挂在 `AgentLoop` 的事件流上当 sink。循环不知道它的存在，只发事件。
- 好处有三个：循环可以脱离可观测性单独测试；加/减轨迹能力不改循环代码；`recorder` 是可选的构造参数，不传就没有。
- 记录粒度是**每个模型步**一条 `StepTrace`（不是每轮对话）—— 一次「工具调用轮」会产生 2 步（模型决定调用 → 模型看完结果再回复），纯回复是 1 步。这个粒度才对得上「第几步改了什么文件」。
- 一个细节坑：`STEP_START` 负责收尾上一步并开新步，**`DONE` 和 `ERROR` 都要收尾** —— provider 抛错时循环直接 return、不 yield `DONE`，如果只认 `DONE`，出错那一步就会丢。

**可能追问**：工具耗时怎么算？→ 用 `list[tuple[工具名, 起始时钟]]` 配对，**不能用 dict** —— 同名工具连续调两次会互相覆写，耗时就对不上了。

### Q15 checkpoint 为什么只覆盖写文件？shell 为什么不能回滚？

**先说**：因为 shell 的副作用范围和成本不可控。

- `write_file` / `edit_file` 的改动边界是明确的 —— 一个文件、内容已知，快照成本可控。
- `shell` 能碰任何东西（建目录、删文件、装依赖、改环境变量、写工作区外的路径）。为每条命令快照整个工作区不现实。
- **关键是把这件事说清楚，而不是假装能撤销**。所以「shell 造成的改动不可回滚」写在回滚报告的结尾，也写在文档里。用户看到报告就知道哪些撤销了、哪些没撤销。

**加分句**：诚实报错比功能完整更重要 —— 一个「看起来能撤销其实撤不干净」的回滚机制，比明确说「不支持」危险得多。

### Q16 `global_step` 是干什么的？为什么要跨重启持久化？

**先说**：让「报告里说的第 3 步」和「回滚命令要的第 3 步」永远是同一个 3。

- 循环每推进一个模型步就把 `step_index` +1；轨迹和检查点**共用**这个全局步号。
- CLI 启动时用 `store.next_step()` 把上次的步号读回来 —— **跨重启不归零**。
- 这样 `loca report` 里看到「第 3 步改了 a.py」，可以直接抄成 `loca rollback <session> 3`，不需要心算。
- 这是我修过的一个真实 bug：早期重启归零，导致同一个会话里出现了两批相同编号的步骤，回滚目标产生歧义。

### Q17 为什么 `list_sessions` 要用 `updated_at DESC, rowid DESC`？

**先说**：因为会话 ID 是「时间戳 + 随机后缀」，按 ID 排序会排错。

- 自动 ID 形如 `20260911-113509-a1b2c3`。**同一秒内创建的多个会话**，按 `session_id DESC` 排出来的顺序是随机的（看随机后缀），于是「最近会话」会指向错误的那条。
- 加 `rowid DESC` 作为次序键，插入顺序才是名副其实的「最近」。这个 bug 影响的是 `loca report` 不带参数时默认报哪一条。
- 教训：**排序键要反映业务含义，不能顺手拿主键用**。

### Q18 工具参数错了怎么办？模型乱传参数你怎么办？

**先说**：用 JSON Schema 校验，不合规就不执行，把错误作为工具结果回灌给模型自己修。

- 每个工具声明 JSON Schema（供 `to_openai_tool()` 转成厂商格式），执行前用 `jsonschema` 校验，不合规抛 `SchemaValidationError`。
- 工具结果统一带 `is_error` 标记，模型能分清「命令失败」和「参数写错了」。
- 路径类参数额外过沙箱校验：必须落在工作区内。

**可以展开的实测结论**：路径沙箱经得起实测 —— `..`、相似前缀（`D:\Projects\loca_evil` 冒充 `D:\Projects\loca`）、`\\?\` 前缀、Windows junction 展开，全部拒绝；而且返回的是**解析后**的路径（检查和操作同一个值，没有「检查 A 写 B」的经典 TOCTOU 漏洞）。

**别踩**：不要说 shell 也沙箱。`shell` 是**故意不沙箱**的（它就是用来执行命令的），这一点我在文档里写明了；`read_file` 那条「模型读不到 `~/.ssh/id_rsa`」的注释只管文件工具的路径边界，不是整项目的安全声明。

### Q19 为什么评测用线程池，不是 asyncio？

**先说**：因为整条链路是同步的，用线程池改动最小、收益一样。

- provider 层是同步 HTTP 客户端（openai SDK 的同步接口），循环也是同步生成器。要并发只能靠线程，或者把 provider 层整体改异步。
- 用 `ThreadPoolExecutor` 的关键配套是：**每个 attempt 自己 new 一个 provider 实例**（不共享 HTTP 客户端状态），每个 attempt 自己的沙箱目录、自己的会话 ID。
- 异步化的收益是「同机并发量更高」，但评测的瓶颈在 API 的响应速度，不在本地线程数 —— 4 线程已经够用。

**可能追问**：那共享 SQLite 会不会写冲突？→ 会，这就是加 `busy_timeout = 5000` 的原因（Q12）。

## 4. 评测集与数据可信度（Week 6，最容易被深挖）

### Q20 为什么要自己造评测集？现成的 benchmark 不行吗？

**先说**：现成的大 benchmark 回答的是另一个问题。

- 比如 SWE-bench 考的是「在真实大仓库里改一个已合并的 PR」——要下仓库、装依赖、跑很久，判据是别人定的，反馈周期以小时计。
- 我需要的是**可控地、几十秒内**回答「我的 harness 现在到底行不行」，这样每改一次代码都跑得起。
- 两者不冲突：大 benchmark 是下一步，自带评测集是日常回归。
- 另一个原因：我不想只报一个总分，我想知道**它每次被什么卡住的**，所以失败分成了七类。

**别踩**：不要说「SWE-bench 不好」。要说「它回答的问题和我的不同」。

### Q21 36 道题怎么设计的？难度怎么分？

**先说**：按「改动半径」分三档，每档考不同的能力。

| 难度 | 题量 | 考什么 | 例子 |
|---|---:|---|---|
| simple | 14 | 单文件定位与修复：读代码、找到那个 bug、精确改一处 | 差一错误、可变默认参数、整数除法、递归基线条件 |
| medium | 12 | 跨文件改动：要同时改多处、理解模块间接口 | 补缺失的 import 并接线、重命名并更新所有调用方、加校验层、加 CLI 参数 |
| hard | 10 | 从零实现数据结构 / 算法，并满足接口契约 | LRU 缓存、拓扑排序、CSV 行解析、罗马数字、表达式求值、Dijkstra、滑动窗口限流 |

- 每题是一个目录：`task.json`（题面 + 元数据 + 判分方式）+ `workspace/`（起始工作区，**故意埋着缺陷**）+ `hidden/`（判分文件）+ `solution/`（参考答案）+ 可选 `checks.py`。
- **难度不是按「代码行数」分的，是按「需要理解的范围」分的**。

### Q22 `hidden/` 是怎么防作弊的？⭐

**先说**：判分文件从不下发给模型，判分前才覆盖回沙箱。

- 跑题时只把 `workspace/` seed 进沙箱，`hidden/` **完全不进去**。模型看不到断言，不知道测试会检查什么。
- 判分时先 `restore_hidden()` **覆盖**回沙箱 —— 所以模型如果在工作区里改了自己的测试文件、甚至写一个同名文件把测试改成 `pass`，都没有用，会被盖掉。
- 有一条测试专门钉住这条性质（"模型改自己的测试文件无效"）。
- `solution/`（参考答案）**绝不 seed 进沙箱**，只用于任务集自检时证明「这题做得出来」。

**别踩**：不要只说「藏起来了」。要说清「判分前会覆盖回沙箱」这一步，这才是防作弊的关键。

### Q23 为什么判分只看行为不看 diff？

**先说**：因为我要测「能不能解决问题」，不是「能不能猜到我心里那份答案」。

- 三种判分方式，都是行为式：
  - `pytest`：把 `hidden/` 的测试套件跑起来
  - `run`：跑命令，比对 stdout 和退出码（`\r\n` 归一化）
  - `script`：调用 `checks.py` 里的 `verify(workspace)`，返回 bool / `(bool, str)` / dict / `CheckResult` 都接受
- 「另一种正确写法也能得分」这一点很重要。如果我比 diff，就等于在考「能不能复现我的实现」，那测的是巧合不是能力。

### Q24 pass@1 和 pass@k 有什么区别？为什么要分开算？

**先说**：它们回答两个不同的问题。

- **pass@1 按「尝试」算**：一次尝试通过的比例 —— 回答「**单次使用**的成功率」。这是用户真实体验到的数字。
- **pass@k 按「任务」算**：一道题在 k 次尝试里至少成功一次的比例 —— 回答「**多试几次**能不能搞定」。
- 混在一起算会得到一个没有意义的数。我这两个指标分开出。
- 成本按「每个**通过**」算（`tokens_per_pass`）。代码里的原话是：**「失败得便宜」不等于「高效」**。如果按「每次尝试」平均，一个很快放弃的模型会显得很省 —— 而那恰恰是没干活。
- 我这轮就有一个现成例子：`impl-word-wrap` **只跑了 4 步**（返回类型错了，判分几乎全挂），token 消耗很低。按尝试平均的话，这个「便宜的失败」会把平均成本往下拉，让报告比实际乐观。
- 报告同时给 `tokens_per_failure`，所以两个数不混：**通过的平均 11,120 tokens，失败的平均 10,751 tokens** —— 失败并不比成功便宜，这本身也是个有意思的观察。

### Q25 七类 outcome 为什么要分这么细？

**先说**：为了知道「它到底被什么卡住了」，而不是只拿到一个分数。

`passed` / `wrong_answer` / `max_steps` / `provider_error` / `timeout` / `crash` / `grader_error`

- 这七类的**处置方式完全不同**：`wrong_answer` 是模型能力问题；`max_steps` 是循环或提示词问题；`provider_error` 是外部服务问题；`crash` 是 harness 有 bug。
- **`grader_error` 单独报警** —— 出题人（也就是我）的 bug 不能算到模型头上。很多自建 benchmark 会在这里糊掉：判分脚本自己抛异常，被当成「模型失败」。
- 还有 `pass@1` 的分母口径要一致 —— 报错重跑、超时这些算不算「尝试过」，我按已定义的口径算，不临时改。

### Q26 91.7% 怎么保证不是自欺？⭐

**先说**：三个机制，每一个都能被验证。

1. **判分文件对模型隐藏**（Q22）：模型看不到断言，改自己的测试文件无效 —— 有测试钉住这条。
2. **判分只看行为不看 diff**（Q23）：测的是「能不能解决问题」。
3. **任务集自检**（Q28）：逐题确认「起始工作区必须判不过、参考答案必须判得过」。起始就能过的题等于没测；参考解都过不了的题报的全是噪音。36 题全部通过。

**再加一句（这是最有力的）**：跑分不是我自己念出来的 —— 原始报告归档在 `docs/benchmarks/deepseek-36.json`，pass@1、分难度数字、每个失败案例的判分详情都在里面。我做审查时**逐条复算过**：`pass_at_1: 0.9167`、`passed_attempts: 33`、三个失败案例的断言计数与文档叙述**逐字一致**。

### Q27 那三个失败说明什么？⭐

**先说**：说明的比分数本身更有用 —— 三个失败**没有一个是因为算法写不出来**。

| 题目 | 难度 | 结果 | 说明什么 |
|---|---|---|---|
| `impl-expression-evaluator` | hard | 16 条过 15 条，只差 `1++2` | 畸形输入的拒绝规则没落实 |
| `impl-word-wrap` | hard | 11 条只过 2 条，**只用了 4 步** | 要求返回「行的列表」，它返回了字符串 |
| `fix-recursion-base-case` | simple | 负数未抛 `ValueError` | 题面写明的边界条件没落实 |

- 共同点是**同一件事**：题面里明确写了的边界条件和返回类型契约，模型没有逐条落实。
- 最有信息量的是 `impl-word-wrap`：**只花了 4 步就交卷**。它不是做不出来，是**没意识到自己没做对** —— 因为判分器是隐藏的，它没有可运行的反馈信号。
- 结论指向 harness 层：**验收标准没有被显式摆到循环面前，循环收工前也没有自己核对一遍**。这比「换个更强的模型」有价值得多。

### Q28 任务集自检是干什么的？为什么能不用 provider？

**先说**：它验证的是「题目本身是不是好的」，不涉及模型。

- 每题要求两个条件同时成立：**起始工作区 → 判分必须不通过**（否则不做也能满分）；**应用参考答案 → 判分必须通过**（否则这题不可解）。
- 两边的判分都不需要模型 —— 判分就是跑 pytest、比 stdout、调 `checks.py`，全是本地行为。所以 **不花一个 token、25.6 秒跑完 36 题**。
- 这挡住两种最隐蔽的坏题。尤其第一种：不做也能满分，而**其它测试全都还是绿的**，不查根本发现不了。
- 我把它做成了常驻命令 `loca bench verify`，可以当常规维护的一部分。

**可能的追问**：那自检本身会不会骗人？→ 会漏一种：**缺参考答案的题**。我现在知道自检对「没有 `solution/` 的题」会判为合格（`ok` 只要求「参考解不是 False」，缺 solution 时是 `None`）。这是我审查发现的缺陷之一，修法是要求「必须实际跑出通过才算合格」（Q37）。

### Q29 11,120 tokens / 5.3 步 是怎么算的？为什么按通过算？

**先说**：`tokens_per_pass` = **通过的尝试的 token 总和 ÷ 通过数** = 366,966 ÷ 33 = **11,120.2**；`steps_per_pass` = 174 ÷ 33 = **5.27**。

> ⚠️ 注意口径：**不是**「总 token ÷ 通过数」—— 那是 399,218 ÷ 33 = 12,097.5，把失败尝试的消耗也算进来了。两个口径的差别正好说明为什么要把通过和失败分开报（理由见 Q24）。

按难度拆开更有意思：

| 难度 | tokens/通过 | 步数/通过 |
|---|---:|---:|
| simple | 8,071 | 4.9 |
| medium | 12,591 | 5.7 |
| hard | 17,901 | 7.1 |

**可以主动说的洞察**：成本随难度**超线性**上升（tokens 从 8k 涨到 18k，是 2.2 倍，而题目复杂度涨得更多）。这意味着「难任务上省 token」的杠杆比「易任务上省 token」大得多。

### Q30 这个评测集有什么局限？（诚实回答）

**先说**：局限很清楚，我说四条。

1. **规模小、场景窄**：36 题都是小规模、单文件或少文件的 Python 改动。没有真实大仓库、没有多语言、没有依赖升级这类任务。
2. **判据是我自己写的**：可能带我的偏好 —— 我写的「正确」不等于「唯一正确」。行为式判分缓解了这个问题，但没有消除。
3. **采样噪声没测**：每一题只跑了 1 次（pass@1 的本义），没有做多次取平均，所以分难度的小样本（hard 只有 10 题）方差没有量化。
4. **提示词与题目是配套调的**：系统提示词是为这类任务写的，换一套题目可能要重调。

**加分句**：所以我从来不把它当成「loca 有多强」的结论，只把它当成「**这次改动有没有让 harness 变差**」的尺子。要证明能力上限，得用 SWE-bench 那类外部基准。

## 5. 工程能力与测试

### Q31 测试策略是什么？406 项怎么组织的？

**先说**：分子系统，离线为默认，联网单列。

- 21 个文件（20 个 `test_*.py` 测试模块 + `__init__.py`），按模块对齐（provider / tools / loop / storage / checkpoint / context / trace / reporter / eval / cli / e2e）。Week 5 新增 104 项（trace 27 / reporter 25 / anthropic 33 / parity 19）、Week 6 新增 82 项。
- **离线是默认**（397 通过 + 1 条件跳过）；真实 API 的 e2e 用 `-m live` 标记，单独跑（8 项通过）。
- `ruff check .` 全绿，line-length 100。

**可能的追问**：测试都在测什么？→ 挑三类说：
- **协议翻译层**：Anthropic 的 33 项全离线（纯函数翻译，不需要网络）
- **跨厂商一致性**：19 项 parity 测试，钉住三家产出同样的工具调用与流式结果
- **性质型测试**（而非例子型）：比如「模型改自己的测试文件无效」「自带任务的 seed 不能等于参考答案」

### Q32 离线/联网为什么分流？跳过的 1 项是什么？

**先说**：离线测试必须在**没有 key 的机器上全绿**，否则 CI 和别人的环境跑不起来。

- `-m live` 的测试要真 key、花钱、慢、还会因为网络不稳定而假红。
- 那 1 项跳过的是 `tests/test_filesystem.py` 里的沙箱测试：它用 `pathlib.Path.home() / ".bashrc"` 当作「工作区外的文件」样本，而系统上没有这个文件（我是 Windows），于是 `pytest.skip`。

**⭐ 这里可以主动暴露一个我刚发现的问题（加分）**：
> 其实这一项 skip 本身就说明了一个小毛病 —— 我的项目是 Windows-only，却拿一个 POSIX 的 dotfile 当测试样本，所以这条断言在目标平台上**永远不会执行**。正确写法是在 `tmp_path` 的父目录之外造一个确定存在的文件，而不是赌 `~/.bashrc` 存在。这是一个「测试能不能跑」被平台细节悄悄决定了的典型例子，和我修过的「`shell` 回退路径测试只断言字符串、从不真的跑命令」是同一类问题。

（这个回答的杀伤力在于：你不但知道 skip 是什么，还知道它是设计缺陷。面试官会觉得你是真的在维护这个项目。）

### Q33 怎么保证改了 A 没弄坏 B？

**先说**：三层。

1. **测试套件**：406 项，离线那套跑得快，改一次代码就能全跑。
2. **性质型回归测试**：专门钉住那些「一旦退化就会静默失效」的地方 —— 跨厂商 parity、防作弊性质、以及**「自带任务的 seed 不能等于参考答案」**（防我自己手滑把答案写回工作区，让题目静默失效 —— 这种错其它测试全都是绿的）。
3. **任务集自检**：`loca bench verify` 不花 token，能挡住「起始就通过」「参考解过不了」这两类坏题。

### Q34 你项目里最难的一个 bug 是什么？怎么定位的？⭐

**先说**：最难的不是想不出来的，是**报错信息本身骗人**的那个。

> 现象：`loca bench run` 带 `--db`（把评测结果落库）时，每一题都被记成 `crash`，失败详情被截断，看不出原因。
>
> 定位过程：
> 1. 先写一个最小复现脚本，只跑一道题、只传 `store_path` —— 拿到完整堆栈。
> 2. 发现是 `TypeError`：`ContextManager.__init__()` 需要一个只读关键字参数 `budget`，而 `run_attempt` 里没传。
> 3. 所以**只要传 `store_path` 就必然崩溃** —— 这条路以前从来没人走过，因为测试都用假 provider 且不落库。
>
> 顺手做的改进：查代码时发现「上下文预算」和「是否持久化」被耦合在了一起。这两件事应该分开 —— 预算要像 `loca chat` 一样独立于 `--no-save`，否则评测测的是一个**没人会用的配置**，测出来的数字没有意义。

**另外两个真实 bug**（都能讲，展示「单测发现不了的边界」这个认知）：
- 步数计数器重启归零 → 回滚目标产生歧义（Q16）
- 同一秒创建的会话排序错乱 → 「最近会话」指向错误（Q17）

**收尾句**：这三个都是**手工跑真实流程**才发现的，单测覆盖不到 —— 因为单测里每个会话都是新建的、时间戳都不同、也都不会带 store。这让我更清楚单测的边界在哪。

### Q35 怎么保证 API key 不进仓库？

**先说**：`.gitignore` 加**提交前的固定动作**。

- `.env`、`.venv/`、`.workbuddy/`、`playground/`、`.loca/` 都在 `.gitignore` 里。
- 固定动作：`git add -A` 之后**先 `git status --short` 审计暂存区**，确认 `.env`（含 DeepSeek key）、`.venv/`、`.workbuddy/` 都没进去，再 commit。
- 还有一条：`.gitattributes` 固定 `* text=auto eol=lf`，避免 Windows 上换行符造成的 diff 噪音。

### Q36 并发跑评测遇到什么问题？

**先说**：一个是库锁，一个是状态共享。

1. **SQLite 写冲突**：4 线程同时写会话库，撞到 `database is locked`。WAL 只降低了概率，最后加 `PRAGMA busy_timeout = 5000` 解决。
2. **状态共享**：每个 attempt 必须自己 new 一个 provider（不共享 HTTP 客户端）、自己的沙箱目录、自己的会话 ID。所以 `run_attempt` 收的是一个 **provider 工厂**而不是一个 provider 实例。

**可能追问**：还有别的吗？→ 还有超时口径。**协作式墙钟超时**只在流式事件之间生效 —— 如果 provider 卡在 HTTP 客户端内部（甚至卡在 shell 命令里），检查根本不会被触发。这一点我写在 `docs/benchmark.md` 里承认了（Q38 会展开）。

### Q37 你这个项目有什么不足？如果重做你会改什么？⭐⭐

**先说**：我做完之后给整个仓库做了一次系统审查，写了一份 26 项缺陷的报告，逐条都复现过。三个 P1：

1. **`shell` 的超时不是上限** —— 声明 `timeout=2s` 的命令实测跑了 8.09 秒。`shell=True` 下超时只终止 `cmd.exe` 这一个进程，真正干活的孙进程还持有 stdout 管道，于是收尾必须等它自己退出。**修法**：Windows 上用 Job Object 或 `taskkill /F /T /PID` 整树杀。
2. **`shell` 的回退路径在它本该生效的场景下 100% 失效** —— `_shell_executable()` 在 `%COMSPEC%` 不是 cmd 时返回裸 `"cmd.exe"`，而 `CreateProcess` 的 `lpApplicationName` 是相对路径时**既不搜 PATH 也不搜 System32**，直接 `FileNotFoundError`。**修法**：回退成 `%SystemRoot%\System32\cmd.exe` 的绝对路径并校验存在。
3. **回滚遇到「同一步内多次改同一文件」会还原成中间版本** —— 同一步内三次 `write_file`（v1→v2→v3）后回滚到该步之前，文件应该被**删除**，实际留下 `v2`。根因是排序只按 `step`，同一步内靠稳定排序保留了「最旧优先」，与函数 docstring 承诺的语义正好相反。**修法**：排序键改成 `(step, id)` 的复合逆序。

**然后说共性（这段最重要）**：
> 三个 P1 有一个共同点：**全都落在边界上** —— 超时、环境变量被改、同一步多次改动。而这些路径单测恰好都绕开了。这让我形成一个习惯：**测试写得绿不代表边界被覆盖了**，我开始专门问「这条路径需要什么前置条件才会被走到」。

**如果面试官问「重做会改什么」**：
> 架构上不太会改，分层我认。会改三件事：① 补权限确认机制（现在 shell 能做任何事）；② 把「上下文预算」和「trace 采集」这类横切能力做得更显式（现在部分依赖可选注入的约定）；③ 一开始就把评测集做进主流程，而不是 Week 6 才补 —— 早一周有尺子，前面几周的设计决策会更可验证。

### Q38 有什么已知 bug？（如果面试官追问「还有呢」）

**先说**：有，我按严重程度排过序，说几个有代表性的。

| # | 问题 | 为什么是问题 |
|---|---|---|
| P2 | `read_file` **没有总量上限** | 只有「单行 4000 字符」限制，行数和文件大小不限 —— 实测一个 5,000 行的文件被整份返回，**290,202 字符**。agent 读个日志就能打爆上下文预算。`shell` 有三重上限（30KB / 500 行 / 2000 字符），`read_file` 一个都没有 |

### Q39 你的 `shell` 超时是怎么实现的？（面试官翻代码式提问）

**先说**：用 `subprocess.run(..., timeout=...)`，但**它现在不构成真正的上限**，这是我知道的缺陷之一。

- 机理：`shell=True` + `executable=cmd.exe` 时，超时只终止 `cmd.exe` 本身；孙进程（`python` / `pytest` / `npm`）继承着 stdout 管道的写端，所以 `communicate()` 必须等孙进程退出才能返回。
- 实测：声明 2 秒，实际 8.09 秒。
- 为什么危险：agent 的循环是同步的，一条 `timeout=30` 的 `pytest` 能把会话挂住几分钟到几小时；而评测那套「协作式墙钟超时」也拦不住 —— 它的检查只在流式事件之间生效，这条路径上根本没有事件。
- 修法就写在报告里：`CREATE_NEW_PROCESS_GROUP` + `taskkill /F /T /PID`，或 Job Object 整树杀。

**加分**：主动补充「我的文档只承认了另一种超时不准确（provider 卡在 HTTP 客户端内部），**没提到 shell 这一种** —— 这也是文档滞后于现实的一处。」

### Q40 你的回滚有没有边界问题？

见 Q37 的第 3 条。补充两个：
- `settled()` 会对本来干净的文件名做一次多余的 `split(" (", 1)[0]`，导致 `docs/report (final).md` 被截成 `docs/report`。那段 split 是历史上为了处理别的格式加的，现在多余的。
- **`shell` 的改动不可回滚**（这是设计取舍，不是 bug，但要主动说清，见 Q15）。

### Q41 你说「三家 parity」，OpenAI 的 token 统计真的对吗？

**先说**：不对，这是审查发现的一条，我直接说。见 Q38 的「OpenAI 流式不请求 usage」。

**要主动承认的一点**：我的离线 parity 测试**结构上测不出这个问题** —— 因为测试用的是假流，我自己补了 usage 帧，所以看起来是通的。这暴露了一个方法论问题：**假数据只能验证「你的代码能处理这种形状的数据」，不能验证「真实服务是否真的会发这种数据」**。

**修法**：payload 里加 `stream_options={"include_usage": True}`，并且加一条「用真实 API 校验 usage 非 0」的 live 测试。

### Q42 你说记录推理内容，代码在哪？

**先说**：文档写了但代码没做 —— `StepTrace.reasoning` 这个字段是**声明了但从不写入**的，循环也从不把推理内容发成事件。

- 这是典型的「文档超前于实现」，我在审查里把它归为 P3。
- 两个选择：要么补齐（DeepSeek 的 `reasoning_content` 已经在 provider 层分离出来了，接到事件流上并不难），要么把文档改掉。
- **我的判断是应该补齐**，因为推理内容对复盘「模型为什么这么决策」很有价值，而且数据已经在手上了，只是没往上传。

### Q43 你的测试覆盖率高吗？有没有「看起来测了、其实没测」的测试？

**先说**：有，而且我举得出具体两处 —— 这正是我审查时最警惕的一类问题。

1. **`shell` 回退路径的那条测试是空头支票**：它只断言 `_shell_executable()` **返回的字符串**是 `"cmd.exe"`，注释写着「对 PowerShell 的 `%COMSPEC%` 免疫」，却**从不真的拿这个返回值跑一条命令**。而那个返回值在真实场景下根本执行不了（Q37 第 2 条）—— 这条测试给了我虚假的安全感。
2. **一条断言因为上游 bug 退化成空断言**：`finish_reason` 恒为 `ERROR`（Q38），导致 `test_deepseek_stream.py` 里一条依赖真实取值的断言**恒不成立**，等于没断言。

**方法论总结（这段很加分）**：
> 这两条的共同点是：**测试通过 ≠ 逻辑被验证**。前者测的是「字符串长得对」而不是「行为是对的」，后者测的是「不抛异常」而不是「值是对的」。我现在会专门检查两种味道：断言里只出现常量或字面量、以及「这个断言有没有可能在所有情况下都成立」。

**还有第三处（平台相关的静默失效）**：沙箱测试拿 `~/.bashrc` 当样本文件，而这是 Windows 项目 —— 这条断言在目标平台上**永远不执行**（就是那 1 项 skip）。见 Q32。

### Q44 这个项目哪些是你参考/借鉴的？

**先说**：设计上有明确的学习来源，我可以说清楚。

- **测试方法论**：`--basetemp` 指到 `%TEMP%`、离线/联网分流这些是行业惯例，我照着用。

### Q45 你项目里踩过什么环境/工程上的坑？

**先说**：挑一个能讲出原理的说 —— `--workspace` 传 Git-Bash 风格路径会被静默解析错。

> `ntpath` 会把 `/d/repo` 当作「盘符相对路径」，解析成 `D:\d\repo`。也就是说你传一个不存在的路径，它**不报错，而是变成另一个空目录**，agent 于是在一个空工作区里干活，你完全不知道。现在 `resolve_workspace()` 会**直接拒绝**这种形态 —— 宁可报错，也不要猜。

**另一个更普遍的坑**：上下文预算和「是否持久化」被耦合了。预算应该独立于落库开关，否则「带落库跑评测」测的是一个没人会用的配置，数字没有意义。

**还有一个值得说的**：开发环境的删除保护会拦掉**项目目录内**的删除（按每轮累计删除数计数，超过阈值就要求确认，非交互时直接抛 `SystemExit`）。后果是在项目目录里跑 pytest 会莫名其妙挂掉一大片测试 —— 看起来像代码 bug，其实完全不是。绕过办法是 pytest 的 `--basetemp` 和所有产物都指到 `%TEMP%` 下用全新路径。

**别踩**：讲环境坑要落到「所以我改了什么」，不要只是抱怨工具。

### Q46 单测发现不了的 bug 你怎么发现？

**先说**：手工跑真实流程，而且专门跑「不常见但真实」的路径。

- 三个真实 bug 都是这样发现的：带 `--db` 跑评测（崩溃）、杀掉进程再启动（步数归零）、同秒创建多个会话（排序错乱）。
- 共同点：**单测里每个对象都是新建的、隔离的、时间戳不同的** —— 而真实使用是「跨进程、并发、有历史状态」的。
- 所以我现在会问自己：「这条路径在生产里会怎么被走到？」然后照着那个前置条件去构造场景，而不是照着函数签名去构造输入。

## 7. 压力题与陷阱题

### Q47 这个项目是不是玩具？能上生产吗？

**先说**：是学习型项目，不能直接上生产 —— 但我清楚差距在哪。

- 要上生产，缺的是：**沙箱与权限确认**（现在 `shell` 能做任何事）、成本预算与配额、多用户会话隔离、密钥托管、并发限流、以及**单用户假设下的所有东西**。
- 但有两块是按生产标准做的：**测试与静态检查是干净的**（406 项、ruff 全绿），**评测是有防作弊设计且证据可复算的** —— 这两点很多玩具项目做不到。
- **诚实的自我定位**：它的价值在「我把 agent 最难的那层亲手写了一遍，并且能用数字说明它现在的水平」。

### Q48 91.7% 是不是因为题目太简单？

**先说**：部分成立 —— simple 组的 14 道题确实偏容易，而且是**故意**的。

- 为什么故意留容易的：它们是**基线可信度锚点**。如果连「修一个差一错误」都过不了，说明 harness 有系统性问题（工具接线、提示词、循环），而不是模型能力问题。有这一档，才能区分「引擎坏了」和「题太难」。
- 但 hard 组 10 道题只有 80% 通过率，涉及 LRU 缓存、拓扑排序、Dijkstra、表达式求值这类从零实现的算法题，**不是简单题**。
- **主动说局限**：36 题不能证明它在真实大仓库上的能力（Q30）。要回答那个问题得用 SWE-bench 这类外部基准。我不拿这个分数当能力上限的结论。

### Q49 一个人 6 周做这么多，是不是有点堆量、深度不够？

**先说**：规模是结果不是目标，我可以给你看深度在哪。

- 深度不在行数，在三处：**协议适配层的纯函数化**（33 项测试不发网络请求）、**异步流式下的重试边界**（用生成器表达「不可逆副作用之前才能重试」）、**评测的防作弊设计**（隐藏判分 + 覆盖回沙箱 + 任务集自检）。
- 而且我自己写了一份 26 项缺陷的审查报告 —— 如果只是堆量求快，我不会回头看，更不会发现那些边界问题。
- **反过来承认**：六周路线图是连续推进做下来的，确实有地方是「先跑通、后深挖」。比如 `read_file` 没有总量上限（Q38），就是当时只想着「先能用」，没想到 agent 读日志会把上下文打爆。

### Q50 如果要你把 loca 用到一个 100 人团队，你会改什么？

**先说**：按「会先出事的地方」排序。

1. **隔离**：`shell` 必须沙箱化（容器或 Job Object），加权限确认 —— 现在等于给了一个任意命令执行入口。
2. **成本**：per-session / per-user 的 token 预算与配额，超限熔断。现在只有「每步」的上下文预算，没有「总共花多少」。
3. **多用户**：会话隔离、并发限流、密钥托管（现在是一个 `.env`）。
4. **审计**：轨迹已经是双写的，但要加上不可篡改与集中汇聚。
5. **稳定性**：修掉那三个 P1（超时整树杀、回退路径、回滚排序），它们在高并发下会被放大。

**可以收尾的洞察**：100 人团队里最容易被忽略的不是「功能不够」，而是「**边界不可控**」—— 超时不可控、副作用不可控、成本不可控。所以我会优先做可控性，而不是加更多工具。

### Q51 你说不用框架，那你怎么知道你的架构是对的？

**先说**：我不确定它「对」，但我知道它**可验证**。

- 架构的正确性体现在两件事上：**能不能独立测试**（协议层能、循环能、观测层能，靠的是可选注入）、**能不能替换**（换 provider 不动循环、换存储不动循环）。
- 另一个判据是**改动成本**：我加一个 provider（Anthropic 完整实现）没有动循环和工具层；加评测框架（`eval/`）复用了真实循环和真实工具，只替换了「题目从哪来」和「谁来判分」。
- **诚实的保留**：`ToolRegistry` 那块名不副实 —— 我的检查发现并没有一个 `ToolRegistry` 类，而是模块级函数，而且 `get()` 零调用（循环用 `self.tools` 线性查找），模块 docstring 还写着 "Week-1 placeholder"。这是设计中没做完的地方。

## 9. 答不上来时的兜底话术

**核心原则**：**不要编**。编错一个技术细节，后面所有回答的可信度都归零。面试官更在意你面对未知的方式，而不是你知道多少。

### 场景 A：完全没接触过的技术

> 「这块我没有实际做过，说不好。我的理解是 [说你能推理出的部分，明确标注这是推理]。如果非要选，我会先去查 X 和 Y 的差异 —— 因为我要判断的是 [你的判断标准]。」
>
> **结构**：诚实承认 → 给出有边界的推理 → 说出你会怎么学。

### 场景 B：记得大概但细节不确定

> 「我记得是 [大意]，但具体到 [那个细节] 我不敢确定，不想给你错的。如果是我的话会去 [查文档 / 跑一遍验证]。」
>
> 这种回答不但不扣分，还显得你**有区分「记得」和「确定」的习惯** —— 这正是这个项目里我最看重的品质。

### 场景 C：被追问到项目里自己没想过的点

> 「这一点我当时没考虑到 —— 你现在这么一说，我觉得 [复述你理解的这个问题]。如果确实是这个问题，那我的 [某个设计] 可能就 [某个后果]。我可以回去验证一下再给你确切答案。」
>
> **注意**：这里千万不要硬答。承认没想到，然后**复述问题**（证明你听懂了）并**推出后果**（证明你会推理）。

### 场景 D：被指出一个真实 bug

> 「对，这个是有的，我在自己的审查里记下来了。根因是 [机理]，修法是 [具体方案]。我没修是因为 [理由，比如排了优先级]。」
>
> 见第 6 节 —— 那些缺陷你都提前知道了，**被指出反而是加分机会**。

### 场景 E：被问「你觉得自己最弱的是什么」

选一个**真实的、可改进的、不致命的**，别选假的弱点（「我太追求完美」），也别选致命的（「我不会写代码」）。

推荐答法：

> 「我很清楚自己单测的边界在哪 —— 我能把逻辑测干净，但真实使用里的时序问题经常漏。我这个项目三个最难的 bug 都是跨进程、并发、带历史状态的场景，单测一个都没抓住。所以我现在会刻意按『生产里这条路径会被怎么走到』去构造场景，而不是按函数签名去构造输入。」

## 10. 白板讲解建议

如果面试官说「你画一下架构」，按这个顺序画（从下往上讲，讲得清楚）：

1. **先画最里面的一圈**：`AgentLoop` 只认识两个东西 —— `LLMProvider` 和「工具列表」。这是设计的核心。
2. **再画三个可选注入**：`checkpoint_manager` / `context_manager` / `recorder`。强调「不传就没有这个能力」。
3. **然后画 Provider 分叉**：OpenAI 兼容层（DeepSeek/OpenAI）和 Anthropic 纯函数翻译层。
4. **最后画旁挂的 eval**：强调它**复用真实循环和真实工具**，只替换「题目从哪来」和「谁来判分」。

架构图（文字版）在第 3 节 Q6，可以直接照着画。

**讲解时最容易加分的两句话**：
- 「这一层我做成纯函数，所以它可以在不发网络请求的情况下被完整测试。」
- 「评测框架没有为测试单独造一套循环 —— 那样测出来的就不是真实的行为了。」
